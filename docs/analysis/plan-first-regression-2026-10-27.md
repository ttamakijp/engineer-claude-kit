# plan-first 低下の原因調査 (2026-10-27)

**調査対象**: plan-first 遵守率が snapshot 2 の 57.8% から snapshot 3 の 22.2% へ
35.6 pt 低下した件。ADR-0015 Step 5 の「指示を戻す」判断の根拠になるため、別調査として
切り出した。

## 結論

**「指示を戻す」は誤り。** plan-first の低下は**指示の効力低下ではなく、分母 (denominator、
率の割る側) に入っている prompt の種類構成が変わったこと**でほぼ説明される。

- **plan を出すことが期待される依頼だけに絞ると、低下は統計的に有意でない**
  (snapshot 2 の 67.2% → snapshot 3 の 60.0%、z=0.45、p=0.65、n=64 vs 10)
- CLAUDE.md §2 の plan-first 指示文は、削減 PR (#83、2026-10-07) と item 4 PR
  (#95、2026-10-27) の前後で **1 文字も変わっていない**
- snapshot 3 の分母 45 件のうち、**35 件は plan を出せない / 出すべきでない行**
  (非依頼行 15 件 + 一行の実行命令 20 件)
- 低下 42.5 pt の内訳は **構成変化 -27.8 pt / 率そのものの変化 -14.7 pt**

したがって対処は**指示を戻すことではなく指標を直すこと**。具体案は §6。

ただし負の所見も 1 つある: `engineer-claude-kit` 単体の plan-first は
62.5% → 14.3% と落ちている (p=0.057、有意水準 5% には届かない)。n が 7-8 件しかなく
判定できないため、snapshot 4 で n を確保して再確認する (§6-5)。

## 1. 元データ

`~/.claude/insights/rule-metrics-baseline-*.json` に記録された 4 点。

| snapshot | 日付 | plan-first | strict | 分母 n | assistant turns | user prompts |
|---|---|--:|--:|--:|--:|--:|
| 1 | 2026-10-06 | 55.6% | 48.6% | 72 | 1,886 | 72 |
| 2 | 2026-10-07 | 57.8% | 50.0% | 64 | 1,608 | 64 |
| 2' | 2026-10-16 | 42.4% | 40.8% | 125 | 3,992 | 126 |
| 3 | 2026-10-27 | 22.2% | 20.0% | 45 | 894 | 46 |

分母は user prompt 数とほぼ 1:1 (72/72、64/64、125/126、45/46)。つまり分母は
**「何件 prompt が来たか」**であり、作業の重さや種類を区別していない。

## 2. 再現方法と妥当性の確認

transcript (JSONL) は残っているため、**4 つの窓すべてを現在のコードで再計算**した。
窓の終端は各 baseline ファイルの更新時刻を使い、当時の切り口と一致させた。

| snapshot | 記録値 | 再計算値 | 差 |
|---|--:|--:|--:|
| 1 (10-06) | 55.6% (n=72) | 62.4% (n=93) | +6.8 pt / +21 件 |
| 2 (10-07) | 57.8% (n=64) | 64.7% (n=85) | +6.9 pt / +21 件 |
| 2' (10-16) | 42.4% (n=125) | 42.5% (n=120) | ±0.1 pt |
| 3 (10-27) | 22.2% (n=45) | 22.2% (n=45) | **完全一致** |

snapshot 2' と 3 は完全に再現した (M1 の実装を独立に再実装した検算でも 42.5% / 22.2%)。
**snapshot 1 と 2 は再現しない。** 現在のコードは当時より 21 件多く prompt を数える。
したがって **snapshot 1 / 2 を 2' / 3 と並べて trend として読むことはできない**
(§6-4 で ADR-0015 への反映を提案)。

以降の比較は、記録値ではなく**一つの定義で再計算した値**を使う。固定定義での系列は:

```
10-06  62.4%   10-07  64.7%   10-16  42.5%   10-27  22.2%
```

固定定義で見ると低下は 64.7 → 22.2 = **-42.5 pt** で、記録値の -35.6 pt より大きい。
低下自体は統計的に実在する (z=4.61、p<0.001)。問題は**それが何の低下なのか**である。

## 3. 仮説ごとの判定

### 仮説 α: 委譲緩和 (delegation relaxation) が plan-first の発火を減らした — 否定

`git log -L` で M1 (plan-first) の計算ブロックの変更履歴を取ると、**導入 commit
(fb59bfd、2026-10-06) 以降一度も変更されていない**。item 4 の PR #95 (02a23ae、
2026-10-27 06:27) が触ったのは M2 (delegation) のみで、M1 は定数も含めて無関係。
snapshot 3 (07:22 記録) は item 4 適用後のコードで動いているが、それでも現在の
コードで完全に再現する。

指示文の側も変わっていない。CLAUDE.md §2 を各時点で取り出して比較した:

| commit | 日付 | §2 の plan-first 行 |
|---|---|---|
| 54000d2 | 2026-10-07 | `実装前に 1 行の修正方針を提示し、承認を得てから着手` |
| 02a23ae | 2026-10-27 | `実装前に 1 行の修正方針を提示し、承認を得てから着手` |

削減 PR #83 は指示面を 39,671 → 16,848 B (58% 削減) したが、**plan-first の指示文は
その削減対象に入っていない**。削減 commit の diff には §2 に触れる行が 1 行も無い。

plan-first を補強する文が他に消えた可能性も調べた。`修正方針` / `着手` を全履歴で
検索すると、この指示が存在するのは**削減前も後も `templates/CLAUDE.md` §2 の 1 行だけ**
である (他の一致は `work-end-reminder.md` の「着手前に確認」と、指標の定義を説明する
`usage-insights/SKILL.md` で、どちらも plan-first の指示ではない)。削減期間に削除された
rule file は `project-skill-recommend.md` 1 件のみで、plan-first には言及していない。

### 仮説 β: local-llm MCP の使用が plan 省略を増やした — 否定

snapshot 3 の窓に `mcp__local-llm__*` の行は 9 件ある。そのうち turn の先頭ブロックに
立ったものは 5 件。しかし **user prompt に応答する turn の先頭に立ったものは 0 件**。

| snapshot | local-llm 行 | turn 先頭 | prompt 応答 turn の先頭 |
|---|--:|--:|--:|
| 10-06 | 0 | 0 | 0 |
| 10-07 | 0 | 0 | 0 |
| 10-16 | 0 | 0 | 0 |
| 10-27 | 9 | 5 | **0** |

M1 は「prompt 直後の turn で text が最初の tool_use より前に出たか」だけを見る。
local-llm 呼出はすべて tool 結果を受けた後続 turn で起きており、M1 の判定に 1 件も
関与していない。**寄与は 0 件で、上限も 0 件。**

### 仮説 γ: 作業 pattern の変化 — 支持 (主因)

分母に入る prompt を種類別に分類した。分類は transcript の本文から機械判定する
(UI 発火の slash command、background task 通知、user が自分の端末で打った
bash-mode 行、skill 起動 payload、compaction 継続、cross-session message 等)。

**分母の構成:**

| snapshot | 分母 | 人間の依頼 | 非依頼行 | 非依頼比率 |
|---|--:|--:|--:|--:|
| 10-06 | 93 | 73 | 20 | 21.5% |
| 10-07 | 85 | 65 | 20 | 23.5% |
| 10-16 | 120 | 100 | 20 | 16.7% |
| 10-27 | 45 | 30 | 15 | **33.3%** |

**人間の依頼だけに絞った plan-first:**

```
10-06  63.0% (46/73)   10-07  66.2% (43/65)   10-16  47.0% (47/100)   10-27  23.3% (7/30)
```

まだ落ちている。しかし人間の依頼の**中身**が変わっていた。依頼の長さで分けると:

| snapshot | 一行命令 (60 字以下) | | briefed な依頼 (60 字超) | |
|---|--:|--:|--:|--:|
| | 件数 | plan-first | 件数 | plan-first |
| 10-06 | 1 | 0% | 72 | 63.9% |
| 10-07 | 1 | 0% | 64 | 67.2% |
| 10-16 | 0 | n/a | 100 | 47.0% |
| 10-27 | **20** | **5.0%** | **10** | **60.0%** |

snapshot 3 の窓では人間の依頼 30 件のうち **20 件が 60 字以下の一行命令**だった。
実例 (当該窓の prompt 列から):

```
PR #2 をマージして
PR #4 をマージして
delete_branch_on_merge も true にして
3 つとも進めて
その方針で進めて
feat/delegation-relaxation を main に rebase して
```

これらは**判断が既に済んでいる実行命令**であり、ここで「修正方針を 1 行」出すのは
CLAUDE.md §2 の意図ではない (§2 は「実装前に」提示せよと書いており、実行指示の
復唱を求めていない)。つまりこの 20 件の「miss」は**指示違反ではなく指示どおり**である。

**briefed な依頼だけで比較すると低下は消える:**

| 比較 | 率 | z | p | 判定 |
|---|---|--:|--:|---|
| 10-07 vs 10-27 | 67.2% vs 60.0% | 0.45 | 0.65 | **有意でない** |
| 10-16 vs 10-27 | 47.0% vs 60.0% | -0.78 | 0.43 | 有意でない |
| 10-07 vs 10-16 | 67.2% vs 47.0% | 2.53 | 0.011 | 有意 |

残った有意差は 10-07 → 10-16 の 1 箇所のみ。これは**project 構成の変化**で説明できる。

**project 別 (人間の依頼のみ):**

| project | 10-06 | 10-07 | 10-16 | 10-27 |
|---|--:|--:|--:|--:|
| `dev-templates` | 66.7% (34/51) | 66.7% (34/51) | 72.9% (35/48) | n=1 |
| `semantic-system` | — | — | **31.2% (10/32)** | — |
| `engineer-claude-kit` | 57.1% (4/7) | 62.5% (5/8) | 16.7% (1/6) | 14.3% (1/7) |
| `hx99g-local-llm` | — | — | — | 100% (4/4) |

全窓に存在する `dev-templates` は 66.7% → 66.7% → 72.9% で**むしろ改善**している
(10-07 vs 10-16: p=0.50、有意でない)。10-16 の低下は `semantic-system` という
新しい project が 31.2% で 32 件分入ってきたことによる。これを除くと:

| 比較 | 率 | z | p | 判定 |
|---|---|--:|--:|---|
| 10-07 vs 10-16 (実測) | 67.2% vs 47.0% | 2.53 | 0.011 | 有意 |
| 10-07 vs 10-16 (`semantic-system` 除外) | 67.2% vs 54.4% | 1.50 | 0.13 | **有意でない** |

**miss の形は全窓で一定:** miss した turn が最初に使った tool を数えると、どの窓でも
Bash が 70-89% を占める (19/27、14/22、47/53、19/23)。「Bash で始まる turn が miss に
なる」という構造は変わっておらず、変わったのは**その種類の turn の割合**である。

### 仮説 δ: 計測不具合 — 形を変えて支持

当初の想定「MCP 呼出を無視したため plan-first の分母が膨らんだ」は**否定**される。
M1 の分母は user prompt 行の数であり、assistant 側の tool 種別に依存しない。MCP を
数えていなかったことは M2 (delegation) にしか影響しない。

一方、調査中に別の計測不具合が 3 件見つかった。

**δ-1: snapshot 1 / 2 が現在のコードで再現しない** (§2)。+21 件、+6.8 pt。
2 点を trend として読むことができない。

**δ-2: 分母に非依頼行が混入している。** 構造的に plan を出せない / 出すべきでない行が
分母に入っており、その比率が窓ごとに 16.7% から 33.3% まで動く。しかも種類ごとの
構造的 plan-first 率が 0% から 100% まで散らばる:

| 種類 | 10-07 | 10-27 | 性質 |
|---|--:|--:|---|
| `interrupt-or-error` | 100% (5/5) | — | 中断後の 1 行応答なので必ず text 先行 |
| `local-command-io` | 0% (0/2) | 100% (2/2) | 内容次第 |
| `ui-slash-command` | 44.4% (4/9) | 50% (1/2) | command の種類次第 |
| `bash-mode-line` | — | **0% (0/5)** | user 自身の端末操作。応答を求めていない |
| `task-notification` | 100% (1/1) | **0% (0/3)** | background task の完了通知 |
| `compaction-continue` | 0% (0/1) | — | 「前置きせず再開せよ」と明示指示される |
| `skill-payload` | — | 0% (0/2) | skill 本文が prompt として記録される |

`compaction-continue` は特に明確で、継続 prompt 自体が「前置きせず直接再開せよ」と
指示する。plan を出さないことが正解であり、それを miss として数えている。

**δ-3: `-ProjectFilter` が部分一致 (`.Contains`) なので親パスが全子を飲み込む。**
`C:\Users\t_tamaki` を project として渡すと配下の全 project に一致するため、
project 別内訳に「全 project の合計」が 1 行混ざる (10-16 の窓で 122 件の行が
row share 0.5% として並ぶという矛盾した出力になっていた)。`C:\dev` も同様。

### 低下の分解

人間の briefed 依頼 (A) / 一行の実行命令 (S) / 非依頼行 (N) の 3 層で、
snapshot 2 の層内率を snapshot 3 の層構成に適用した反実仮想を置く。

| | A: briefed | S: 一行命令 | N: 非依頼 |
|---|--:|--:|--:|
| 10-07 の層内率 | 67.2% | 4.5% (全窓 pooled) | 60.0% |
| 10-27 の構成比 | 22.2% | 44.4% | 33.3% |

```
観測     10-07 64.7%  ->  10-27 22.2%        合計 -42.5 pt
反実仮想 (10-07 の率を 10-27 の構成に適用)   37.0%
  構成変化による分   -27.8 pt  (65%)
  率そのものの変化   -14.7 pt  (35%)
```

S の 10-07 側は観測 1 件しかないため全窓 pooled (1/22) を使った。層が粗く、
snapshot 3 の n が小さいため、この 65:35 という配分には幅がある。確かなのは
**構成変化が主因で、率の変化は従**という向きである。

## 4. 仮説の判定まとめ

| 仮説 | 判定 | 根拠 |
|---|---|---|
| α 委譲緩和が plan-first を減らした | **否定** | M1 ブロックは導入以降未変更。§2 の指示文も 1 文字も変わらず。snapshot 3 は現コードで完全再現 |
| β local-llm 使用が plan 省略を増やした | **否定** | 9 件中、prompt 応答 turn の先頭に立ったものは 0 件。寄与の上限が 0 |
| γ 作業 pattern の変化 | **支持 (主因)** | 低下の 65% が構成変化。briefed 依頼のみでは 67.2% → 60.0% で有意でない (p=0.65) |
| δ 計測不具合 | **形を変えて支持** | 想定した機序ではないが、別に 3 件 (snapshot 1/2 非再現、非依頼行の混入、ProjectFilter 部分一致) |

## 5. ADR-0015 Step 5「戻す」の判定

**戻すべきではない。** 根拠:

1. 削減 PR #83 は指示面を 58% 削ったが、**plan-first の指示文はその削減対象に
   入っていない** (§3 α)。戻す対象と低下の因果が成立しない
2. plan を出すことが期待される依頼に絞ると、**削減前 (snapshot 2) と削減後
   (snapshot 3) の差は統計的に有意でない** (67.2% vs 60.0%、p=0.65)
3. 唯一有意だった 10-07 → 10-16 の低下は、`semantic-system` という project が
   mix に入ったことで説明され、除外すると有意性が消える (p=0.011 → p=0.13)
4. 全窓に存在する `dev-templates` の plan-first は削減をまたいで **66.7% → 72.9%**
   で、低下していない

つまり現状の数字は「指示を削ったら守られなくなった」証拠になっていない。PR #83 を
戻すだけで常時ロードに 22,823 B (39,671 - 16,848) が復活し、その後の削減まで戻せば
30,166 B (39,671 - 現在の 9,505) になるが、その見返りを示す測定値が存在しない。
ADR-0015 の原則「足す前に測る」をそのまま適用すると、**戻す前に指標を直す**のが順序。

**ただし保留が 1 つ:** `engineer-claude-kit` 単体では 62.5% → 14.3% と落ちており、
p=0.057 で有意水準に僅かに届かない。n が 7-8 件しかないため「有意でない」は
「差が無い」ではなく「判定できない」を意味する。kit 自身の作業が多い窓で n を
確保して再確認する必要がある (§6-5)。

## 6. 対処案

指標を直す方向。優先順に。

1. **分母から非依頼行を除外する。** `New-RuleMetricsRow` で prompt の種類を判定し、
   UI 発火 command / background task 通知 / bash-mode 行 / skill payload /
   compaction 継続 / cross-session message を分母から外す。構造的に plan を
   出せない行を遵守率の分母に入れてはいけない。影響は大きい (snapshot 3 の分母 45 →
   30、比率 33.3% が除外される)
2. **一行の実行命令を別層にする。** 60 字という閾値は暫定で、閾値そのものを
   snapshot 4 で検証する。少なくとも「plan を期待する依頼」と「実行命令」を分けて
   報告し、集約率を単独で出すのをやめる。集約率は prompt の構成を測っており、
   遵守を測っていない
3. **`-ProjectFilter` を leaf 一致にする。** 部分一致のままだと親パスが全子を飲み、
   project 別内訳が信用できない (§3 δ-3)
4. **ADR-0015 の snapshot 表に snapshot 1 / 2 の非再現を明記する。** 現コードでは
   +21 件 / +6.8 pt ずれる。1 / 2 を 2' / 3 と trend として並べないこと
5. **report に分母の構成を出す。** 「分母 45 件 = 人間の依頼 30 (briefed 10 /
   一行命令 20) + 非依頼 15」を併記すれば、率だけを見て誤読するのを防げる。
   これは `compare-snapshots.ps1` が eligible 数の倍率を警告するのと同じ発想
6. **snapshot 4 で `engineer-claude-kit` 単体の n を確保する。** §5 の保留を解く。
   n=30 程度あれば 62.5% → 14.3% 相当の差は検出できる

1-3 と 5 は実装 PR、4 は docs PR。local-llm 系 PR (a)/(b)/(c) とは独立しており、
どの順でも入れられる。

## 7. 付録: 本調査の限界

- snapshot 3 の窓は n=45 (briefed 依頼は n=10) と小さい。briefed 依頼での
  「有意でない」は差が無いことの証明ではなく、**この n では検出できない**という意味。
  60.0% の 95% 信頼区間は [31.3, 83.2] と広い
- prompt の種類判定は本文の先頭パターンによる機械判定で、取りこぼしがある。
  実際、最初の試行では `<task-notification>` / `<bash-input>` / bash-mode 行 /
  skill payload を「人間の依頼」に誤分類しており、非依頼比率を 6.5% と
  過小評価していた (正しくは 33.3%)。現在の分類も網羅の保証はない
- 60 字という長さ閾値は snapshot 3 の prompt を見てから決めたもので、事後的である。
  §6-2 のとおり閾値自体を次の窓で検証する
- 3 層分解の層内率は、S 層で全窓 pooled を使っている (10-07 側の観測が 1 件のため)。
  65:35 という配分には幅がある
- plan-first は ADR-0015 §E のとおり proxy (代理指標) であり、どの指示ファイルが
  実際にロードされたかは transcript に残らない。本調査はその proxy の分母を正した
  だけで、指示の効力そのものを直接測ってはいない

## 再現手順

本調査の測定スクリプトは scratchpad に置いた一時的なものだが、要点は以下で再現できる。

```powershell
# 窓を固定して再計算する (窓の終端は各 baseline ファイルの更新時刻)
. .\scripts\usage-insights.ps1
$all = Get-InsightsScope -WindowDays 40 -IncludeRuleMetrics
$slice = @($all | Where-Object {
    $t = ([datetime]$_.Timestamp).ToLocalTime()
    $t -gt [datetime]'2026-10-20T07:22:38' -and $t -le [datetime]'2026-10-27T07:22:38'
})
Get-RuleMetrics -Entries $slice
```

prompt 種別の内訳と briefed / 一行命令の分離は現時点では指標側に入っていない。
§6-1 と §6-2 を実装すれば `usage-insights.ps1` の出力として直接得られる。
